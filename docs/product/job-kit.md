# ReproPilot 求职表达包

## 简历项目描述

**ReproPilot｜机器学习论文复现与代码修复智能体｜独立开发**

- 构建以状态机驱动的论文复现 Agent，将 PDF 证据抽取、论文—代码配置审计、Docker 隔离执行、错误诊断、最小补丁、测试验证和结果对比串成可审计闭环；每次修改保存 Git diff、命令日志和 artifact 引用。
- 设计 7 维复现可信度评分与高风险人工审批：指标、数据划分、模型和 checkpoint 等语义修改必须绑定补丁 SHA-256；真实 ResNet-20/CIFAR-10 checkpoint 评估得到 Error `8.27%`，论文值为 `8.75%`，系统判定 `80/100 PARTIAL`，明确不等同于从头训练复现。
- 建立 3 个开源仓库、6 个注入故障的 Agent 基线，获得 `6/6` 定位与 `6/6` 修复后语义探针通过；访谈并测试 5 位真实参与者，根据 `2/5` 误解可信度分数等发现迭代审批证据和拒绝状态语义。

## 30 秒介绍

ReproPilot 不是论文问答工具，而是让机器学习论文项目真正运行并判断结果可信程度的 Coding Agent。它接收论文、仓库、数据和环境，在受限 Docker 中审计配置、执行代码、诊断错误、生成最小补丁并验证，最后按七个证据维度生成报告。项目最关键的设计是把“代码跑通”和“论文复现成功”分开：即使数字接近，如果只验证了公开 checkpoint，结果仍会被标成 PARTIAL。

## 3 分钟 STAR 讲解

### Situation

复现失败通常分成两类：显式报错，以及程序正常结束但数据划分、指标或配置已经偏离论文。通用问答工具能解释报错，却缺少跨论文、代码、运行证据和结果的统一状态。

### Task

目标是做一个作品集级 Agent：能够在 10–20 分钟缩小实验内完成闭环，同时保存证据、控制修改范围，并对“复现成功”给出有边界的判断。

### Action

我把流程实现为状态机；原仓库和数据只读挂载，补丁只写工作副本。系统先跑最小命令，失败后定位相关文件，生成 diff，按风险决定自动验证或暂停审批；审批与 SHA-256 绑定。结果阶段不只比较数字，还检查环境、数据、配置、指标、种子、接近度和依赖。随后我建立故障注入基线，并用五位真实参与者测试产品原型。

### Result

工程基线在限定的 6 个案例中实现 6/6 定位和修复后探针通过，真实 checkpoint 案例生成 80/100 PARTIAL 报告。用户测试发现 2/5 会误解分数、拒绝补丁后状态冲突；第二版因此加入永久解释、数值样例、断言与日志，并修正为 STOPPED。限制是样本小、基线规模有限、真实案例未从头训练，不能宣称通用自动复现。

## 高频追问

### 为什么不是普通论文问答？

问答的输出主要是文本；ReproPilot 的输出是可执行状态变化和证据 artifacts。它必须运行不可信代码、处理失败、控制补丁、执行测试，并把论文声明与实际命令和结果对应起来。

### 80/100 怎么算？

七个维度总权重为 100：环境 15、数据 20、配置 20、指标 15、随机种子 10、结果接近度 15、外部依赖 5。每个得分必须引用 artifact；证据部分满足只能得部分分，缩小实验不能靠“数字接近”拿满分。

### Agent 如何避免乱改代码？

只向工作副本应用补丁；限制相关文件；每次保存 diff；应用前做风险分类；应用后运行目标测试和最小命令；失败就回滚；语义高风险修改必须人工审批且绑定补丁哈希。

### 一个失败或取舍案例是什么？

公开 checkpoint 的三个 seed 得到完全相同结果。产品没有把它包装成稳定的三次训练，而是明确说明这只是三个独立评估进程，不能证明训练过程可复现，因此最终仍是 PARTIAL。
