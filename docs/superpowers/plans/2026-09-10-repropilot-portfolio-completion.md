# ReproPilot Portfolio Completion Plan

> 本文件是执行时制定的历史计划，未同步勾选的条目不代表当前状态。最新的逐项验证结果见 [`docs/product/completion-audit.md`](../../product/completion-audit.md)。

> 历史执行说明：当时要求 agent 按 checkbox 逐项实施；当前请以交付审计为准，不要从本文件的未勾选项重新启动旧任务。

**Goal:** 把 ReproPilot 从“技术 MVP + 本地产品原型”完善为可以放进简历、让面试官打开、并且所有结论都有证据支持的 AI 产品作品集。

**Architecture:** Python CLI 与 Docker 是真正执行论文复现的核心；运行日志、Git diff、测试结果和评分文件是证据层；React 网页是解释执行过程、审批高风险补丁和阅读报告的交互层。作品集第一版允许网页使用去敏冻结数据，但必须用真实 CLI 运行和演示视频证明底层 Agent 确实工作。

**Tech Stack:** Python 3.11+、Pytest、Docker Desktop/WSL 2、Git/GitHub Actions、React、Vite、OpenAI 兼容 API、Markdown、HTML。

**Spec:** `docs/superpowers/specs/2026-09-08-product-case-foundation-design.md`

## Global Constraints

- 不把“代码运行成功”写成“论文完整复现成功”。
- `80/100` 是复现证据可信度，不是模型准确率。
- 用户研究只能记录真实参与者回答，禁止生成模拟访谈数据。
- API Key 只能放在本机环境变量中，禁止写进仓库、截图或演示视频。
- 高风险语义补丁必须经过人工审批，并绑定补丁 SHA-256。
- 作品集第一版不实现账号、计费、云 GPU 调度和多人协作。
- 每个工程阶段必须有可重复命令、测试结果和 Git 提交。

- [ ] 至少 5 位真实参与者完成访谈并留下匿名记录。
- [ ] 至少 5 位参与者完成原型可用性测试。
- [ ] 产品指标报告展示真实人数、中位数、范围和失败案例。

满足以上条件后，可以在简历中把它描述为“完整 AI 产品作品集”。网页动态连接后端属于第二版增强，不阻塞第一版完成。

## 阶段 0：GitHub 与安全收尾（第 1 天）

### Task 0.1：合并 GitHub PR #5

**负责人：** Codex 独立完成；只有 GitHub 要求额外授权时才需要你操作。

**底层逻辑：** 你的电脑里有本地 Git 仓库，GitHub 上有远程仓库。只有把 Pull Request 合并进远程 `main`，其他人打开 GitHub 才能看到正式版本。

- [ ] 确认 [PR #5](https://github.com/yihanx082-cmd/ReproPilot/pull/5) 的 CI 为绿色。
- [ ] 合并 PR，并删除远程功能分支。
- [ ] 执行 `git pull --ff-only`，确认本地与 GitHub 一致。
- [ ] 执行 `git rev-list --left-right --count origin/main...main`。
- [ ] 验证输出为 `0 0`。

**验收标准：** GitHub `main` 与本地 `main` 指向同一提交，工作区干净。

### Task 0.2：轮换 DeepSeek API Key

**负责人：** 你必须完成账号操作；Codex 负责检查配置和仓库。

**底层逻辑：** API Key 相当于模型账户密码。曾经发送到聊天中的 Key 应视为已经暴露，即使暂时没人使用。

- [ ] 登录 DeepSeek 开放平台。
- [ ] 删除或停用旧 Key。
- [ ] 创建新 Key；不要把 Key 发到聊天中。
- [ ] 在 PowerShell 中设置以下三个环境变量：

```powershell
$env:OPENAI_API_KEY="你的新 Key"
$env:OPENAI_MODEL="deepseek-v4-pro"
$env:OPENAI_BASE_URL="https://api.deepseek.com"
```

- [ ] Codex 执行只显示文件名、不显示命中内容的凭据扫描。

**验收标准：** 旧 Key 不可用，仓库没有任何真实密钥。

## 阶段 1：Docker 与工程证据闭环（第 1–2 天）

### Task 1.1：恢复 Docker Desktop Linux 引擎

**负责人：** 你只负责启动 Docker Desktop；Codex 负责诊断和测试。

**你要做：** 当 Codex 提醒时打开 Docker Desktop，等待界面显示 Engine running。

- [ ] 检查 `wsl -l -v` 中 `docker-desktop` 状态。
- [ ] 检查 `docker version` 同时显示 Client 和 Server。
- [ ] 运行 `docker run --rm hello-world`。

**验收标准：** Docker Server 可连接，hello-world 正常退出。

### Task 1.2：运行 Docker 集成测试

**负责人：** Codex 独立完成。

```powershell
$env:REPROPILOT_DOCKER_TESTS="1"
$env:REPROPILOT_DOCKER_BIN=(Get-Command docker.exe).Source
pytest tests/test_sandbox.py tests/test_orchestrator.py -q
```

- [ ] 验证只读论文/仓库/数据集挂载。
- [ ] 验证工作副本可写。
- [ ] 验证命令超时终止。
- [ ] 验证日志中的秘密被脱敏。
- [ ] 保存最终测试数量与运行时间。

**验收标准：** Docker 专属测试没有失败或错误。

### Task 1.3：完成一次可录制的真实运行

**负责人：** Codex 执行；你观看并学习关键节点。

- [ ] 验证论文解析证据。
- [ ] 验证论文—代码配置差异。
- [ ] 验证最小运行、诊断、补丁和测试循环。
- [ ] 验证正式实验、指标比较和可信度报告。
- [ ] 记录运行命令、run ID、artifact 路径和总耗时。

**你重点学习：** 为什么最小运行先于正式实验、Git diff 如何限制修改范围、测试通过为什么仍不等于论文复现成功。

**验收标准：** 从一条 CLI 命令生成完整 `report.html` 和可审计 artifacts。

**底层逻辑：** `127.0.0.1` 只代表你自己的电脑，电脑关机后别人无法访问。公开部署会把构建产物放到持续运行的托管服务器。

- [ ] 执行 `npm ci`、`npm test`、`npm run build` 和 `npm run test:sites`。
- [ ] 部署 `prototype` 构建产物。
- [ ] 用无痕窗口验证公开网址。
- [ ] 检查手机和 1024 px 桌面宽度下没有严重裁切。
- [ ] 把公开网址加入 README 和产品案例。

**验收标准：** 未登录 GitHub、未安装 Python 的陌生人也能打开完整点击流程。

### Task 2.2：整理 GitHub 首页

**负责人：** Codex 独立完成，你负责判断自己是否能读懂。

- [ ] README 首屏在 30 秒内说明问题、输入、输出和差异化。
- [ ] 加入原型链接、演示视频位置和报告截图。
- [ ] 分开说明“真实 Agent”“冻结网页原型”和“未来动态连接”。
- [ ] 保留安装、运行、测试、限制和安全模型。

**验收标准：** 不了解项目的面试官能回答：它解决什么问题、怎么工作、证据是什么、当前有什么限制。

## 阶段 3：真实用户研究（第 4–8 天）

### Task 3.1：邀请 5 位参与者

**负责人：** 你独立完成；Codex 提供邀请话术和记录模板。

**建议对象：** 做过课程论文复现、毕业设计、科研训练或机器学习项目的学生、研究人员和工程师。

- [ ] 邀请至少 7 人，以保证最终有 5 人完成。
- [ ] 不诱导对方说项目有用。
- [ ] 说明只记录匿名内容，不收集仓库密码或数据集。
- [ ] 使用 `docs/product/interview-kit.md`。

**验收标准：** 获得 P01–P05 五份真实、可匿名引用的回答。

### Task 3.2：完成问题访谈

**负责人：** 你提问和记录；Codex 在收到去身份化内容后分析。

- [ ] 先询问最近一次真实复现经历，不先介绍 ReproPilot。
- [ ] 记录耗时最大的步骤、失败点、使用工具和判断成功的方法。
- [ ] 询问错误修复后如何确认实验语义没有改变。
- [ ] 记录原话或忠实摘要，不写推测。
- [ ] 删除姓名、学校、公司、邮箱和私人仓库地址。

**验收标准：** 每位参与者至少包含一个具体事件、一个痛点和一种当前替代方案。

### Task 3.3：形成研究发现

**负责人：** Codex 独立分析，你确认解释是否符合原意。

- [ ] 对回答进行主题编码。
- [ ] 区分高频问题、严重但低频问题和单人意见。
- [ ] 所有结论同时展示分子和分母，例如 `4/5`。
- [ ] 更新 `docs/product/research-findings.md`。
- [ ] 根据证据调整 PRD 优先级。

**验收标准：** 不再出现 `Awaiting real participant responses`，每条发现可追溯到匿名记录。

## 阶段 4：原型可用性测试（第 8–10 天）

### Task 4.1：让 5 位参与者完成核心任务

**负责人：** 你主持和观察；Codex 准备表格并计算指标。

- [ ] T1：创建任务并进入范围确认。
- [ ] T2：指出一个论文—代码差异。
- [ ] T3：解释为什么高风险补丁需要暂停。
- [ ] T4：根据 diff、影响和测试作出审批决定。
- [ ] T5：解释 `PARTIAL`、未解决风险以及为什么 80/100 不是准确率。

主持时不要告诉参与者应该点哪里。只有对方无法继续时才提示，并记录提示时间和内容。

**验收标准：** 每位参与者都有完成情况、理解用时、是否求助、决策理由和满意度记录。

### Task 4.2：计算产品指标

**负责人：** Codex 独立完成。

- [ ] 任务完成率。
- [ ] 理解当前状态的中位时间与范围。
- [ ] 人工步骤减少量。
- [ ] 高风险决策正确人数。
- [ ] 报告正确理解人数。
- [ ] 满意度中位数、范围和理由。

**验收标准：** 小样本只报告人数、中位数和范围，不进行统计显著性外推。

### Task 4.3：完成一次有证据的产品迭代

**负责人：** Codex 修改与测试；你确认是否解决参与者问题。

- [ ] 选择影响人数最多或风险最高的一个问题。
- [ ] 先写可复现问题或自动测试。
- [ ] 只修改相关界面和文案。
- [ ] 重新运行前端测试、浏览器流程与视觉检查。
- [ ] 在案例中记录“发现—决策—修改—验证”。

**验收标准：** 产品案例至少包含一次由真实用户证据推动的迭代，而不是只展示初版设计。

## 阶段 6：第二版产品化增强（不阻塞求职，可在第一版完成后进行）

### Task 6.1：让网页连接真实 ReproPilot

**负责人：** Codex 主导实现；你参与需求和验收。

- [ ] 设计最小本地 API：创建任务、读取状态、读取事件、审批、读取报告。

- [ ] 使用 Server-Sent Events 或轮询显示真实事件。
- [ ] 保留冻结 demo 模式，方便无 Docker 环境演示。
- [ ] 增加端到端测试证明浏览器操作会创建真实 run artifacts。

**验收标准：** 用户从网页提交本地样例后，Docker 实际运行并把证据实时显示在时间线中。

### Task 6.2：扩展 Agent 评测集

**负责人：** Codex 独立完成，你参与解释指标。

- [ ] 从 3 个仓库扩展到至少 5 个小型项目。
- [ ] 增加组合故障，而不只测试单故障。
- [ ] 报告定位率、修复率、无关修改率、成本和工具调用次数。
- [ ] 记录失败案例和不能自动修复的边界。

**验收标准：** 评测不只报告成功案例，并且可以从配置重复运行。

## 阶段 7：并行补齐 AI 产品经理基础能力

这部分不属于 ReproPilot 代码，但建议每天投入 30–45 分钟。

### SQL 学习顺序

- [ ] 第 1–2 天：`SELECT`、`WHERE`、`ORDER BY`、`LIMIT`。
- [ ] 第 3–4 天：`GROUP BY`、`COUNT`、`SUM`、`AVG`。
- [ ] 第 5 天：`INNER JOIN`、`LEFT JOIN`。
- [ ] 第 6 天：用条件聚合计算转化漏斗。
- [ ] 第 7 天：用日期分组和自连接理解留存。
- [ ] 第 8–10 天：用 ReproPilot 的任务事件表完成一份产品指标分析。

**验收标准：** 能在面试中写出基础查询、分组、漏斗和次日/七日留存，并解释指标口径。
