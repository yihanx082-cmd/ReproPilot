# ReproPilot Agent 性能评测与记忆升级规格

## 1. 背景

ReproPilot 已经具备论文证据抽取、代码配置审计、隔离运行、错误诊断、最小补丁、目标测试、语义探针、结果对比和可信度报告等完整链路。现有冻结评测集包含 3 个真实开源仓库和 6 个故障案例，已经测得错误定位、修复成功和修复后探针均为 `6/6`。

这组结果能证明系统在这些案例上可以完成任务，但不能单独证明以下结论：

- “诊断 → 补丁 → 测试 → 反馈”的循环优于单轮生成；
- 上下文管理能够提升多步修复成功率；
- 历史修复记忆能够跨仓库迁移；
- 性能提升了某个确定的百分点。

原因是现有 6 个案例全部在第一次模型调用后成功，存在明显的天花板效应；同时，当前真实评测的重试逻辑没有把上一次验证失败完整反馈给下一次模型调用。

## 2. 升级目标

本轮升级只解决一个核心问题：**用可复查的对照实验，证明 ReproPilot 的 Agent 机制是否真正提升任务成功率，并量化代价。**

完成后，系统应能回答：

1. 结构化诊断是否优于只把原始报错交给模型？
2. 测试失败反馈是否能帮助模型完成多阶段修复？
3. 仅保存“已经通过验证”的历史经验，是否能提升跨仓库修复表现？
4. 成功率提升是否伴随更多模型调用、Token、时间或无关代码修改？

## 3. 不在本轮范围内

- 不为了技术栈关键词引入 Redis、ChromaDB、RAG 框架或 Multi-Agent。
- 不改写现有论文解析、正式实验和可信度评分主流程。
- 不把小样本结果包装成统计显著性结论。
- 不预设或承诺“提升 12.9 个百分点”。所有简历数字必须来自保存的原始实验结果。
- 不把 API Key、仓库源码或未脱敏日志写入记忆库或提交到 GitHub。

## 4. 实验设计

### 4.1 固定输入

沿用现有冻结仓库、提交和故障补丁，组合为 3 个多阶段案例：

| 案例 | 冻结仓库 | 阶段 1 | 阶段 2 |
|---|---|---|---|
| `convmixer-progressive` | `locuslab/convmixer-cifar10@2d3d9b7` | 缺少依赖 | 数据集路径错误 |
| `resnet-progressive` | `akamaster/pytorch_resnet_cifar10@d5489e8` | 学习率配置不一致 | Top-1 指标实现错误 |
| `lightning-progressive` | `karasawatakumi/pytorch-image-classification@4dd1870` | CPU/CUDA 选择错误 | 验证集被随机打乱 |

两个故障在实验开始时同时注入，但评测器每次只返回当前最靠前的失败阶段。修复阶段 1 后，阶段 2 才会暴露。这种设计模拟真实工程中“修完一个阻塞错误后才看到下一个错误”的过程。

### 4.2 四组对照

| 组别 | 输入给模型的上下文 | 最大模型调用数 | 目的 |
|---|---|---:|---|
| `single_turn_raw` | 原始失败信息、允许修改路径 | 1 | 最弱基线 |
| `diagnosis_single_turn` | 原始失败信息、结构化诊断、相关文件 | 1 | 测量诊断贡献 |
| `feedback_loop` | 结构化诊断、每轮补丁、测试失败、回滚状态 | 3 | 测量反馈循环贡献 |
| `episodic_memory` | `feedback_loop` 全部信息 + 两条跨仓库验证经验 | 3 | 测量记忆贡献 |

四组必须使用相同模型、温度、仓库、提交、案例顺序和安全边界。正式实验建议每组每案例运行 3 次；若预算不足，可以先运行 1 次形成工程证据，但报告必须明确样本量。

### 4.3 防止数据泄漏

- 记忆组使用 leave-one-repository-out：不能检索当前仓库及同一提交产生的经验。
- 只记录探针通过、修改范围合规且工作树清洁的修复。
- 记忆内容只保存错误签名、根因摘要、验证过的补丁、探针摘要和仓库身份，不保存密钥。
- 所有组使用同一份冻结 manifest；运行后不得手工挑选成功案例。

## 5. 上下文与记忆设计

### 5.1 工作上下文

每次补丁请求包含以下有界字段：

```text
CURRENT_FAILURE
STRUCTURED_DIAGNOSIS
ALLOWED_PATHS
RELEVANT_FILE_EXCERPTS
PREVIOUS_PATCH
VERIFICATION_FAILURE
ROLLBACK_STATUS
RETRIEVED_VERIFIED_EXPERIENCES
```

字段不存在时输出明确的 `none`，避免模型把缺失信息当成隐含成功。文件内容、日志和历史经验都设置长度上限，确保上下文可预测并方便复现。

### 5.2 经验记忆

使用 Python 标准库 SQLite，而不是额外部署 Redis 或向量数据库。第一版数据结构：

```python
@dataclass(frozen=True)
class RepairExperience:
    id: str
    category: str
    error_signature: str
    stack_tags: tuple[str, ...]
    root_cause: str
    failed_diffs: tuple[str, ...]
    verified_diff: str
    probe_summary: str
    repository_url: str
    commit_sha: str
    model: str
    created_at: str
```

检索先按故障类别过滤，再根据错误签名与技术标签的词项重合度排序，默认返回 2 条。该方案足以验证“跨任务经验能否带来收益”，也便于面试时解释；只有在数据规模和检索评测证明必要后，才考虑向量检索。

## 6. 指标

### 6.1 主指标

- 完整任务成功率：两个阶段全部修复且所有探针通过的案例数 / 总案例数。
- 阶段解决率：已通过阶段数 / 总阶段数。
- 安全完成率：完整成功、未越过允许路径、无未批准高风险改动的案例数 / 总案例数。

### 6.2 质量与成本指标

- 错误定位率；
- 修复后探针通过率；
- 无关修改行比例；
- 平均补丁尝试次数；
- 模型调用次数；
- 输入与输出 Token；
- 墙钟时间；
- 记忆命中数和命中后成功数。

报告中的提升统一写成“百分点”，例如：

```text
反馈循环完整成功率 7/9，单轮基线 5/9，提升 22.2 个百分点。
```

分数必须同时展示分子和分母。样本较小时只描述观察结果，不使用“显著提升”等统计推断措辞。

## 7. 产物与证据链

每次实验生成独立时间戳目录，至少包含：

- `ablation-results.json`：逐次运行的原始事实；
- `ablation-summary.md`：四组汇总和差值；
- `ablation-report.html`：面试展示版本；
- 每个案例的失败输出、诊断、补丁 diff、测试输出和探针结果；
- 实验配置快照：manifest 哈希、代码提交、模型、重复次数和运行时间。

简历、README 和作品集中的性能数据只能由 `ablation-results.json` 生成，禁止手工填写未经验证的数字。

## 8. 验收标准

- 四组实验能够在假模型下确定性跑通，测试覆盖多阶段反馈、回滚、越界修改和记忆泄漏防护。
- 3 个冻结仓库的双故障均能成功注入，并能按顺序暴露两个阶段。
- 单轮组严格只有一次模型调用；循环组和记忆组最多三次。
- SQLite 只记录验证成功的修复，且不会返回同仓库同提交经验。
- 报告中的计数、百分比、百分点差和成本可由原始 JSON 重算一致。
- 没有新的密钥或实验缓存被 Git 跟踪。
- 使用真实模型前必须配置新的本地 API Key；已经在对话中暴露过的旧 Key 不得继续使用。

## 9. 面试表达边界

在实验完成前，可以写：

> 设计“诊断—最小补丁—目标测试—语义探针”闭环，并构建单轮、反馈循环与跨任务记忆的消融评测框架。

实验完成后，才可以根据真实结果写：

> 在 3 个冻结真实仓库的 N 次多阶段修复实验中，反馈循环将完整任务成功率从 A/B 提升至 C/D（+X.X 个百分点），同时将无关修改率控制在 Y%。

如果记忆组没有提升，也应如实报告，并分析检索相关性、案例规模和经验覆盖不足，而不是删除该组结果。
